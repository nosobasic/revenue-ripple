Proposed capability role: rr_retention_writer, NOLOGIN NOINHERIT NOSUPERUSER

Exact table capabilities, RLS constrained to live acct_1RHozW2Ku9STqdAd:
 rr_retention_catalog: SELECT only.
 rr_retention_bindings: SELECT only.
 rr_retention_evidence: SELECT + INSERT only; existing FK/unique/check constraints.
 rr_retention_review_holds: SELECT + INSERT only, bound live-account users only.
 No UPDATE/DELETE/TRUNCATE on those tables; no profile/content/CRM/AI grants.
 Catalog/bootstrap bindings and clearing holds remain explicit owner operations.
The writer is a trusted billing authority: it can append plausible evidence for
already bound users; SQL cannot itself verify a Stripe signature or canonical API
response. Runtime code isolation, restricted secrets and exact provider policy are
part of the trust boundary. RLS alone does not prevent a compromised writer from
fabricating evidence for its permitted bindings. This must be accepted explicitly.

One non-public SECURITY DEFINER capability lock_bound_user(uuid) takes the existing
user row lock only if a live-account binding exists; returns only that UUID or NULL,
uses empty search_path and qualified names; no dynamic SQL. EXECUTE only to writer,
never PUBLIC/client/service roles. Function owner is postgres in the LOCAL fixture;
production review must pin ownership and body and ensure no private-schema CREATE
privilege for worker. This avoids granting UPDATE on profile rows merely to lock.
